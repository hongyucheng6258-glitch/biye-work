# 端到端业务闭环与测试可靠性设计

## 目标

修复上一轮端到端验证中暴露的真实业务缺口和测试误判，使学生端、管理端、通知中心、文件上传、AI、私信与 3D 校园的关键链路可以被准确验证，并在 Docker 环境重新验收。

## 范围

本轮只处理以下范围：

1. 闲置预约：创建预约、卖家通知、卖家处理、双方完成、互评和拒绝后重新上架。
2. 举报：学生提交、管理员查看和处理、举报者收到对应处理通知、学生查看自己的举报记录。
3. 失物认领与校园问答：使用正确业务类型，验证状态字段和处理通知。
4. 私信图片：先通过上传接口创建当前用户拥有的资源，再验证图片消息发送和读取。
5. 登录、退出和验证码：修正 UI 测试的认证状态判定，确保页面行为与接口行为一致。
6. 并发与 3D：使用真正并行请求验证互斥状态；覆盖 3D 校园进入房间、手动打开服务、返回房间和普通学生端数据可见。
7. Docker 验收：验证容器内 API、前端、数据库、Redis、上传资源和 WebSocket 的可用性。

不在本轮范围内：清空数据库、重新生成演示数据、修改视觉设计、替换 AI 提供商、重构无关模块。

## 设计

### 产品闭环

所有业务操作必须同时满足三项：操作接口返回成功；数据库状态改变为预期值；相关用户收到带有正确 `type`、`bizType`、`bizId` 的通知。通知测试必须按业务 ID 匹配，不能只检查消息列表接口返回 200。

闲置预约的状态顺序固定为 `待确认 → 已接受 → 已完成 → 可互评`，拒绝路径为 `待确认 → 已拒绝`，并将物品恢复为在架。测试为买家和卖家分别确认完成，不能在买家完成后把卖家拒绝当成产品失败。

举报处理使用后端现有管理路由。学生侧增加或校验“我的举报”查询能力，管理员处理成功后发送包含举报 ID 的结果通知，前端可从消息进入对应记录。

### 测试可靠性

测试辅助函数统一解包 `data.list`、`data.records` 和数组响应，并为状态字段提供明确的 API 断言。截图只能作为视觉证据，不计入业务功能通过数。

并发场景使用 `Promise.all` 或等价并行请求，断言数据库最终只能产生一个有效预约、活动报名不超过上限、重复操作返回业务错误。测试数据使用带前缀的临时记录，结束时只删除本轮创建的数据。

上传测试保存返回的资源 ID 和地址，在服务重启或容器重建后再次读取；私信测试把该资源 ID 传给聊天接口，验证归属校验和消息内容。

3D 测试使用稳定的语义选择器或显式数据属性，逐步验证页面状态，而不是仅检查 canvas 存在。进入房间后内容必须由“打开服务内容”按钮触发，返回房间不得重置到校园初始点，普通端查询必须看到同一业务数据。

### 错误处理

接口失败时记录 HTTP 状态、业务码、响应消息和请求上下文；脚本找不到前置数据时记录 BLOCK，不得无条件记录 PASS。AI 和外部服务失败测试使用隔离配置，不能修改当前运行环境的生产或 Docker 配置。

### 验收标准

1. 原始 9 个 FAIL、1 个 BLOCK、2 个 UNCOVERED 均有明确结论：修复并通过、确认是预期拒绝、或记录为有理由的 BLOCK。
2. 预约和举报通知按对应业务 ID 验证。
3. 并发测试确实同时发起请求，并检查最终数据库状态。
4. 上传图片在服务重启后仍可读取，私信图片消息可以发送和查看。
5. 3D 房间流程和普通学生端同步均有可复现的自动化证据。
6. Docker 服务健康检查、后端接口、学生端和管理端页面均通过，且不执行清库。
